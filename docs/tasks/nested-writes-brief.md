# 작업 지시서: Nested Writes (`관계형 중첩 쓰기`) — 설계 브리핑

> **[리뷰어 확정 완료 - 2026-08-19]**:
> - **채택 옵션**: **옵션 B (순차 생성 + 보상 롤백)** 로 공식 확정.
> - **채택 근거**: `storage.Store` 인터페이스 변경 없이 기존 Blob rollback 패턴(Task 4.4)을 그대로 재사용 가능하며, Go/Cloudflare 양쪽 패리티 구현 난이도가 낮고, 짧은 중간 상태 노출 트레이드오프는 `drink-log` 같은 개인 소유 레코드 중심 서비스에서 감수 가능함.
> - **자식 개수 상한**: `?include=`와의 일관성을 위해 부모당 최대 50건으로 확정.
> - **사전 검증 (Pre-validation)**: 부모 생성 전 자식 레코드 전체에 대해 스키마 검증, 권한 검증(`auth.Evaluate(ActionCreate)`), 50건 상한 검증을 선행하여 롤백 발생 확률을 최소화함.
> - **응답 형태**: 생성 성공 시 별도 재조회 왕복 없이 생성된 부모와 자식 레코드 전체를 embed 형태(예: `"images": [...]`, `"record_tags": [...]`)로 포함한 201 Created 일체형 응답 반환 확정 (`?include=` 표준 응답 형태와 일관성 유지).

## 1. 배경 (왜 이 작업을 하는가)

`drink-log` 실제 운영 중 관찰:

* **쓰기(Write) 경로가 읽기보다 훨씬 심각**: 사케 기록 1건 저장 시 `부모 레코드
  POST → 이미지 N건 POST 루프 → 태그 매핑 M건 POST 루프`로 이어지며, 실측
  결과 요청 1건당 **최소 6회, 많게는 10회 이상의 순차 HTTP 요청**이 발생함.
* **원자성 부재**: 이 순차 요청 중간에 네트워크가 끊기면 부모만 생성되고
  자식이 없는(또는 그 반대의) 고아 레코드가 남는다. 현재 코어에는 이를
  되돌릴 방법이 없다 — Blob 1-step create의 `HardDeletePhysically` 롤백이나
  Cloudflare Target의 R2 보상 삭제(Task 4.4)처럼, **여러 레코드에 걸친 쓰기를
  묶어주는 장치가 관계형 자식 레코드에는 아직 없다.**

이 정도의 반복 횟수와 실패 시 무결성 리스크는 "아직 발생하지 않은 문제"가
아니라 **매 쓰기 요청마다 실제로 겪고 있는 구조적 한계**이므로, 마세라티
원칙이 경계하는 선제적 추상화에 해당하지 않는다고 판단한다 (`client-writable-
field-brief.md` 6절과 같은 논리).

## 2. 문제의 정확한 스코프

* **다루는 것**: `has_many` 관계로 선언된 자식 레코드들을 부모 레코드 생성과
  **한 번의 HTTP 요청**으로 함께 쓰는 것. 실패 시 부모/자식 전체가 일관된
  상태로 남는 것(전부 성공 또는 전부 실패).
* **다루지 않는 것 (명시적 제외)**:
  - **`?include=` 조회 확장**: 별도 문제이며 이미 Task 5.5로 해결된 belongs_to
    `?include=`와 충돌하지 않게 별도 브리핑으로 다룬다.
  - **Blob 필드의 JSON 자동 스트리밍**: `docs/ir-spec.md` 5.5절이 명시적으로
    blob을 JSON payload 경계 밖(멀티파트/업로드 서브 엔드포인트)에 둔 이유가
    있고, 실측으로도 이미 프로덕션에서 별도 해결됨. 이번 작업은 blob 필드를
    건드리지 않는다 — nested writes의 자식 레코드가 blob 필드를 가지고
    있더라도, 그 필드는 기존처럼 별도 업로드 경로를 그대로 쓴다.
  - **2단계 이상 깊이의 중첩** (자식의 자식을 함께 쓰는 것): 아래 3.1절 스코프
    제약 참고.
  - **`belongs_to` 관계의 중첩 쓰기** (예: 자식 생성 시 부모를 함께 생성):
    `ownership_field` 자동 주입 및 FK 무결성 순서상 의미가 불분명해 스코프 밖.

## 3. 설계 옵션

### 3.1 공통 스코프 제약 (모든 옵션에 적용)

* **`has_many` 1-depth만 지원**: 부모 리소스가 선언한 `has_many` 관계의 자식
  레코드 배열만 허용한다. 자식의 자식(2단계 중첩)은 지원하지 않는다 — 지금
  `?include=`가 `belongs_to`만 허용하는 것과 대칭적인 스코프 축소이며, N:M
  Join Resource(`RecordTag`)는 "자식의 자식"이 아니라 "또 다른 has_many
  자식"으로 취급해 1-depth 안에 들어온다.
* **자식 개수 상한**: 관계당 최대 N건(제안값: 50건, `?include=`와 동일한
  기준 검토)으로 제한하고 초과 시 `400 TOO_MANY_NESTED_RECORDS`로 거부한다.
  무제한 배열을 받아들이면 단일 요청의 실행 시간과 트랜잭션 크기가 통제
  불가능해진다.
* **기존 검증/보안 규칙 100% 재적용**: 자식 레코드 각각에 대해서도 다음이
  부모와 동일하게 적용되어야 한다 (새 경로를 만들지 않고 기존 경로를 재사용):
  - `ValidateRecord`의 타입/제약 검증
  - `client_writable: false` 필드 거부 (Task 8.2)
  - `ownership_field` CREATE-time 자동 주입 (Task 8.1) — 자식도 세션 사용자로
    고정하며, 부모가 아니라 부모와 동일하게 세션에서 가져온다.
  - 자식 리소스의 `auth.permissions.create` 평가 (부모의 `ActionCreate` 통과가
    자식의 권한을 대신하지 않는다 — 자식 리소스가 별도로 `create: role:admin`
    처럼 잠겨 있다면 nested write도 동일하게 403이어야 함).
* **FK 자동 바인딩**: 자식 배열의 각 항목에는 부모 FK 필드(`record_id` 등)를
  요청 payload에 넣을 필요가 없다 — 부모 생성 후 발급된 PK로 서버가 자동
  주입한다. 클라이언트가 값을 보내더라도 `ownership_field` 자동 주입과 동일한
  원칙으로 무시하고 서버 값으로 덮어쓴다(위조 방지).

### 3.2 옵션 A — 원자적 DB 트랜잭션 (Go 런타임: SQLite Tx / Cloudflare: `D1.batch()`)

부모 INSERT와 자식 INSERT 전체를 하나의 DB 트랜잭션(또는 D1 배치)으로 묶어
실행한다. 하나라도 실패하면 전체가 롤백된다.

**장점**:
- 진짜 원자성. 중간 상태가 절대 관찰되지 않는다.
- Cloudflare Target은 `D1.batch()`가 이미 원자적 배치를 지원하므로 구현
  난이도가 상대적으로 낮다.

**단점 / 리스크**:
- **Go 런타임 쪽이 더 큰 작업**: 현재 `storage.Store` 인터페이스(`Create`,
  `Update`, `List`, ...)는 단일 레코드 단위 오퍼레이션으로 설계되어 있고
  트랜잭션 경계를 노출하지 않는다. `Store`에 `WithTx`류의 메서드를 추가하는
  것은 Milestone 2가 확립한 "Store(관계형 CRUD)와 BlobStore(바이트 저장)는
  서로 다른 책임" 원칙과는 별개로, **Store 인터페이스 자체의 계약 변경**이라
  더 신중한 검토가 필요하다.
- 검증(타입/제약/`client_writable`/`ownership_field`/권한)을 트랜잭션 내부에서
  수행해야 하는데, 지금 이 검증 로직들은 HTTP 핸들러 레이어(`transport/
  handler.go`)에 있다. 트랜잭션 경계 안으로 끌어들이거나, 트랜잭션 시작 전에
  전체 검증을 미리 다 마쳐야 한다(사전 검증 후 커밋 방식).
- 두 Target(Go/Cloudflare) 간 트랜잭션 원자성 보장 메커니즘이 근본적으로
  다르다(네이티브 SQL 트랜잭션 vs D1 배치) — 패리티 테스트가 반드시 필요하다
  (`cloudflare-codegen-review.md`의 "커버리지 격차 점검" 체크리스트 적용 대상).

### 3.3 옵션 B — 순차 생성 + 보상 삭제 (Compensating Deletion)

부모/자식을 순차적으로 `Create` 호출하되, 자식 생성 중 하나라도 실패하면
그때까지 생성된 레코드(부모 포함)를 역순으로 하드 삭제하여 롤백을 흉내낸다.

이것은 이미 Blob 1-step create의 원자적 롤백(`docs/ir-spec.md` 5.5절
`HardDeletePhysically`)과 Cloudflare Target의 다중 Blob 보상 삭제(Task 4.4,
`uploadedBlobKeys` 추적)가 쓰고 있는 **기존에 검증된 패턴과 동일한 접근**이다.

**장점**:
- **기존 아키텍처 패턴 재사용** — `storage.Store` 인터페이스 변경이 필요
  없다. 각 자식은 지금처럼 독립적인 `Create` 호출이고, 실패 시 정리 로직만
  핸들러 레이어에 추가하면 된다.
- Go/Cloudflare 두 타깃에 동일한 패턴을 그대로 이식할 수 있어 패리티 확보가
  상대적으로 쉽다.
- 검증 로직(`ValidateRecord`, `client_writable`, `ownership_field`, 권한 평가)을
  전혀 건드리지 않고 기존 단일 레코드 경로를 그대로 N번 호출하면 된다.

**단점 / 리스크**:
- **진짜 원자성이 아니다** — 롤백 도중 다른 요청이 중간 상태(부모는 있지만
  자식 일부만 있는 상태)를 짧게 관찰할 수 있다. Blob 롤백에서도 동일하게
  "수 ms간 레코드가 관찰될 수 있음"을 알려진 제약으로 남겼던 것과 같은
  트레이드오프.
- 롤백 자체가 실패할 경우(삭제 중 오류) `BLOB_STORE_FAILED_RECORD_PRESERVED`와
  유사하게 "정리 실패, 레코드 보존됨"을 명시적으로 알리는 에러 코드가
  필요하다 — 이 또한 기존 패턴 재사용.

### 3.4 옵션 C — 코어 확장 없음, 클라이언트 병렬 요청 가이드만 제공

Nested Writes를 코어에 넣지 않고, 클라이언트가 자식 요청들을 순차가 아니라
`Promise.all` 등으로 병렬 전송하도록 가이드 문서만 추가한다.

**장점**: 코어 변경 0줄.

**단점**: 요청 횟수(6~10회)는 줄지 않는다 — 병렬화해도 원자성 문제는 그대로
남고, 실측으로 보고된 "고아 레코드" 리스크도 해결되지 않는다. 사실상 문제를
풀지 않는 것에 가깝다 (client-writable 브리핑의 "옵션 B는 사실상 Task 8.2를
안 하는 것" 판정과 같은 종류의 논리).

## 4. 옵션 비교 요약

| 항목 | 옵션 A (DB 트랜잭션) | 옵션 B (순차 생성 + 보상 삭제) | 옵션 C (코어 미확장) |
| :--- | :--- | :--- | :--- |
| 원자성 보장 수준 | 완전 | 근사 (짧은 중간 상태 가능) | 없음 |
| `storage.Store` 인터페이스 변경 | 필요 | 불필요 | 불필요 |
| 기존 검증/권한 경로 재사용 | 재구조화 필요 | 100% 그대로 재사용 | 해당 없음 |
| Go/Cloudflare 패리티 구현 난이도 | 높음 (메커니즘 상이) | 낮음 (동일 패턴 이식) | 해당 없음 |
| 기존 아키텍처 선례 | 없음 | 있음 (Blob rollback, Task 4.4) | 해당 없음 |
| 요청 횟수 감소 효과 | 1회로 완전 통합 | 1회로 완전 통합 | 없음 (병렬화만) |

**초안 의견 (확정 아님, 리뷰어 판단 필요)**: 옵션 B가 기존 아키텍처 패턴과의
정합성 및 구현 리스크 면에서 우위로 보인다. 다만 "짧은 중간 상태 노출"이
`drink-log`처럼 개인 소유 레코드 중심 서비스에서는 감수 가능한 리스크인지,
아니면 진짜 트랜잭션이 필요한 수준인지는 **사람의 판단이 필요한 지점**이다.

## 5. 애매했던 지점 (리뷰어 확정 필요)

1. **자식 개수 상한값**: 50건을 제안했으나 근거는 `?include=`와의 일관성일
   뿐, `drink-log` 실사용 패턴(레코드당 평균/최대 이미지 수, 태그 수) 기준
   데이터는 없다. 실측 후 조정 필요.
2. **응답 형태**: 생성된 부모+자식 전체를 응답으로 돌려줄 것인가(현재
   `?include=`와 동일한 embed 형태), 아니면 부모 ID만 반환하고 클라이언트가
   재조회하게 할 것인가. 전자가 왕복을 더 줄이지만 응답 스펙이 하나 더
   늘어난다.
3. **부분 실패 시 에러 응답 형태**: 어떤 자식이 실패했는지(`index`, 필드명)를
   얼마나 구체적으로 알려줄 것인가 — Milestone 2 회고의 "에러 메시지
   명확성" 원칙과, 너무 상세한 에러가 정보 유출로 이어지지 않는지의 균형.
4. **옵션 A/B 최종 채택**: 위 4절 비교표 기준으로 사람이 최종 확정.
